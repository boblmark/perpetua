# 跨平台爆款内容采集与分析方法论流水线

把「8 平台爆款数据」从零做到可交付的完整流程。本技能沉淀自一次真实执行
（288 行有效数据 / 5 平台成功 / 3 平台附失败证据），**包含大量踩坑记录与已验证的可用接口**，
能显著减少重复试错。

---

## 0. 先读这一节：三条铁律（违反即报废）

> 这套流水线的唯一价值是**数据可信**。任何一次估算都会让整份交付失去意义。

1. **只填页面/接口公开可见的数字。看不到就写 `N/A`。绝不估算、绝不编造、绝不用"约/大概/推算"。**
2. **不采集、不推断任何后台指标** —— 完播率、留存率、点击率、流量来源、粉丝画像。这些平台不公开，任何"估算值"都是编的。
3. **不确定就标注**。OCR 未识别 ≠ 封面无文字；小样本结论必须写"仅作方向参考"。

**红线检查**：`views` 与 `likes` 全为 `N/A` 的行**视为无效行**，必须剔除。
**自检**：交付前，任取 5 行，用 `video_url` 打开原视频对数字 —— 对不上就是 bug。

## 3. 四阶段流水线（标准执行顺序）

```
① 采集        →  ② 规范化        →  ③ 分析          →  ④ 交付
collectors       rows.json          analysis.json      xlsx + 文档
（按平台）      （统一契约）        （统计口径）        （可复核）
```

### 阶段契约（这是本流水线的核心设计）

各平台采集脚本**只需产出统一契约的 JSON**，后续所有环节与平台解耦：

```jsonc
// <platform>_rows.json  ── 平台行数据
{ "rows": [ { /* 见 templates/field-spec.md 的 20 字段 */ } ],
  "accounts": [ /* 可选：账号清单 */ ] }

// analysis.json ── 统计结果（供出表/写文档复用，保证文档与数据一致）
{ "interaction": [...], "topic": [...], "hook": [...],
  "duration": [...], "title_len": [...], "cover": [...],
  "series": [...], "top_tags": [...], "notes": [...] }
```

**空值统一写字符串 `"N/A"`**（不要留空、不要用 null），便于出表时零空单元格。

### 抽样的关键规则

- **爆款组 / 对照组必须在同一账号内、同一时间窗内切分**（按该账号的播放量中位数切）。
  跨账号比较毫无意义 —— 账号量级差 100 倍会污染结论。
- 对照组 = 该账号同期**中位数附近**的作品，不是"最差的作品"。
- 平台不公开播放量时（抖音），**改用点赞量排序**，并在 `sampling_frame` 字段如实标注口径。

## 5. 环境准备与自检

```bash
bash scripts/setup_env.sh            # 一键：Agent Reach + 文档依赖 + gh CLI + 补系统库
bash scripts/setup_env.sh --browser  # 额外装浏览器路线（~713MB，仅小红书需要）
bash scripts/self_test.sh            # 端到端自检（用 example_data 跑通全链路）
```

### 关于"环境丢失"

沙箱/容器的工作区快照通常**不保留** `~/.cache`、`~/.local`、venv、`/tmp`、`site-packages`。
**每次新会话都要重跑 `setup_env.sh`。** 只有工作区内的常规文件会持久化。

### Chromium 缺系统库（高频问题）

新容器常缺 `libnspr4.so` 等库，且无 root 无法 `apt-get install`。
**这会影响 PDF 生成**（Playwright 渲染），不只是爬虫。

```bash
bash scripts/fix_chromium_libs.sh                 # 自动探测缺失库并补齐（多轮直到干净）
bash scripts/run_with_libs.sh python3 xxx.py      # 带库运行任意命令
```

原理：`apt-get download`（**不需要 root**）取 .deb → `dpkg-deb -x`（**不需要 root**）解包到本地目录
→ 用 `LD_LIBRARY_PATH` 指过去。库缓存在 `~/.pipeline_libs`。

### 数据目录解析（可移植性）

所有脚本通过统一解析器定位数据，**不依赖绝对路径**：

```
优先级：$PIPELINE_DATA > . > 脚本目录 > 各级上级目录 > <上级>/collector > <上级>/example_data
输出目录：$PIPELINE_OUT（默认数据目录的上一级）
```

迁移到新任务时：
```bash
export PIPELINE_DATA=/path/to/your/data    # 放 *_rows.json 和 analysis.json
export PIPELINE_OUT=/path/to/output
```

### 快速验收

```bash
bash scripts/self_test.sh
# 预期：288 行 / 空单元格 0 / 11 个 sheet / 5 类交付物全部生成
```

## 7. 分析层要点（最容易做错的地方）

- **互动率 = 互动数 ÷ 播放量**，取**组内中位数**（不是平均，避免被极端值带偏）。
- **不要假设"爆款互动率更高"**。实测中 B站 爆款 3.40% vs 对照 3.40%（几乎相同）、
  快手 **对照反而更高**。爆款赢在**绝对触达**，不在单位效率 —— 这是必须写进结论的发现。
- **小样本必须做显著性检验**（置换检验，20000 次重排）。若 28 项检验只有 1 项 p<0.05，
  要主动指出"28 项检验本就约会出现 1.4 项假阳性"，不能把噪声当规律。
- **封面结论要敢说"无规律"**。像素级指标若普遍不显著，就如实写，这比编一条"爆款配色"更有价值。

详见 `references/09-analysis.md`。

## 8. 常见失败模式（血泪清单）

| 症状 | 真实原因 | 解法 |
|---|---|---|
| B站详情接口返回 `-412` | 未做 wbi 签名 | 用 `bili_lib.py` 的签名实现 |
| 抖音 `play_count` 恒为 0 | 平台不公开播放量 | 不是 bug；写 N/A，改用点赞排序 |
| 小红书全部 302→404 `sec_*` | 缺 `xsec_token` 或浏览器指纹不符 | 用带指纹的 Chromium v148，或走纯 HTTP 签名路线 |
| 小红书搜索/主页返回 `-101` | **服务端要求登录**（不是签名问题） | 只能上登录态，别再花时间调签名 |
| 小红书粉丝显示 `10+ 粉丝` | **登录态占位值，不是真实数据** | 绝不采用，如实记 N/A |
| 快手 `?pcursor=N` 翻页失败 | 触发验证码（`400002`） | 放弃翻页，用现有池子并标注上限 |
| 浏览器报 `Bus error` / `missing section headers` | **下载/解压被超时中断**，二进制截断 | 重下并让解压**完整跑完**，勿设短超时 |
| 文档里的数字与 xlsx 不一致 | 手抄数字 | 文档必须从 `analysis.json` 生成，禁止手写数值 |
