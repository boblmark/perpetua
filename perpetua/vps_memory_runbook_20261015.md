# VPS 内存告急处理单（2026-10-15）

观测：2026-10-15 15:18 CST，你 VPS 终端截图显示内存 92%、swap 100% 已满、
另有 "System restart required" 待办。本地 VM 内存正常（可用约 3.8GB/7.9GB），
压力只在 VPS 侧。

下面命令在**你自己电脑**的终端执行（你可直接 `ssh` 上 VPS，本机研究环境出站被限、动不了 VPS）。

## 0. 先复核现状（只读，30 秒）
```bash
free -m
```
- 若 Mem available 回升到 >15% 且 swap 明显下降 → 已自行缓解，下面不用做。
- 若仍是 90%+ / swap 满 → 继续。

## 1. 找吃内存的大户（只读）
```bash
ps aux --sort=-%mem | head -12
```
记下 %MEM 最高的前 3 个进程名。

## 2. 安全释放（不杀进程，可逆）
```bash
sync && echo 3 | sudo tee /proc/sys/vm/drop_caches
free -m   # 再看一次
```
说明：这只清文件 pagecache，**清不动 swap**。swap 100% 满只能靠重启
或杀掉吃内存的进程解决，这一步只是低成本先试。若 `sudo` 无权限，跳过此步。

## 3. 若仍 >90%：二选一，你拍板

**A. 先扛着（保今晚 23:30 档）**
- 代价：生成高峰期 OOM Killer 可能随机杀进程（Chrome 9344 / mcp-b / 隧道），
  届时靠 keepalive 自动拉起，会丢几分钟。
- 适合：available 还有 800MB 以上。

**B. 现在重启（彻底）**
```bash
sudo reboot
```
- 重启后 VPS 侧服务**不会**自己全回来，必须按 Rule 11 清单逐项拉起并验证：
  `18739 / 18736 / 8734 / 8735 / 8080 / 8740(dispatcher) / 9344(Chrome)`、
  各反向隧道 ssh 进程；每项 `ss -ltnp` 确认 LISTEN 再 `curl` 健康接口 200。
- 预计中断 10~15 分钟，期间生成任务排队等待（不丢，mcp-b 队列在）。
- 适合：available < 800MB，或第 1 步发现某个进程内存泄漏式增长。

经验规则：available < 800MB 选 B，否则选 A 扛过今晚、明早低峰再 B。

## 4. 做完告诉我的信息（我好继续盯）
- 选了 A 还是 B
- 第 1 步看到的 TOP3 进程名（判断是不是泄漏）
- 若选 B：重启后各端口是否都回来了
